  - **Проблема:** Сценарий: Запрос отправлен с токеном клиента, не владеющего указанной картой. Заголовок раздела указывает HTTP-статус 403 Forbidden, однако текст под заголовком и пример ответа определяют возврат кода 404 Not Found (Карта не найдена). Разработчик и тестировщик получат разный результат при определении HTTP-кода ответа.
  - **Как исправить:** Привести заголовок и описание к единому коду ответа: либо использовать 404 Not Found с сообщением Карта не найдена (и переименовать заголовок), либо использовать код 403 Forbidden.

  > «### Блок согласующих» — строка 87
  - **Проблема:** В наборе требований пропущены: требования к аудиту/логированию действий, детальные условия производительности под нагрузкой, требования к безопасности/правам доступа, схема отката/отключения функционала, а раздел «Тестирование требований» содержит заглушку «заполняются тестировщиками». ## 8. Итог

**Можно ли начинать разработку и тестирование: НЕТ — начинать разработку и тестирование по документу в текущем виде нельзя.**

Начинать разработку и тестирование по текущему документу нельзя из-за критических противоречий в API-контрактах (D-010, D-033, D-040) и отсутствия метода чтения настроек (D-028). В бизнес-логике присутствуют не устраненные неоднозначности и пробелы, касающиеся статусов карт, типа транзакций и обработки возвратов (D-002, D-003, D-005, D-016, D-021). Кроме того, не определены требования к безопасности и аудиту, а раздел тестирования содержит заглушки (D-013, D-014, D-036, D-038, D-043, D-044).

**Что исправить в первую очередь:**

1. Устранить противоречия в кодах ответов и структуре API: согласовать HTTP-статусы (200, 400, 403, 404), формат ответов для ошибок/успеха, использование Content-Type и тела запроса. *(D-010, D-033, D-040, D-038)*
2. Добавить в спецификацию REST API эндпоинт/параметры для чтения текущих настроек порога уведомлений и унифицировать типы данных (integer vs string) полей amount и enabled. *(D-028, D-036)*
3. Уточнить бизнес-логику: определить критерии активной карты, момент проведения покупки (авторизация/списание), начальное значение порога по умолчанию, поведение при изменении порога и логику сброса флага push при возврате транзакции. *(D-002, D-003, D-005, D-016, D-021)*
4. Добавить в требования спецификацию по безопасности, аутентификации, правам доступа, маскированию чувствительных данных, логированию/аудиту действий и схеме отката. *(D-013, D-044)*
5. Заполнить раздел «Тестирование требований» и расширить критерии приёмки, добавив проверки для возвратов, значений по умолчанию, повторных триггеров push, SLA доставки и граничных значений порогов. *(D-014, D-043)*
